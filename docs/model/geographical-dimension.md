# Географическое измерение — иерархия и уровни
*Geographical Dimension — Hierarchy and Levels*

> **Статус: Draft / Черновик.** Проектное описание; не подтверждено импортом схемы в Oracle Data Modeler.

| Параметр | Значение |
|---|---|
| Проект | Global11_demo |
| Измерение | `GEOGRAPHY` |
| Иерархия | `GEO_ROLLUP` |
| Предполагаемый источник | `GLOBAL.CUST_ACCOUNT` |
| Происхождение источника | Физическая таблица, сформированная CTAS из `CUSTOMER_DIM` и `ACCOUNT` по `ACCOUNT_ID` |

## 1. Назначение

Географическое измерение группирует клиентские точки отгрузки по местоположению и позволяет анализировать показатели от страны до конкретного получателя (*Ship-To*).

В многомерной модели возможны два варианта реализации:

1. Отдельное измерение `GEOGRAPHY`, если географическая иерархия должна повторно использоваться в нескольких кубах.
2. Иерархия внутри `CUSTOMER`, если географический анализ всегда выполняется в контексте клиента.

Выбор варианта не зафиксирован и требует проверки существующего `CUSTOMER_DIM` и требований аналитики.

## 2. Источник данных и атрибуты

Предполагаемый источник — `GLOBAL.CUST_ACCOUNT`. Согласно описанию демонстрационных изменений, таблица создаётся объединением `GLOBAL.CUSTOMER_DIM` и `GLOBAL.ACCOUNT` по `ACCOUNT_ID`.

| Уровень | Ключ уровня (предварительно) | Источник |
|---|---|---|
| Страна | `COUNTRY` | `CUST_ACCOUNT.COUNTRY` |
| Штат / провинция | `(STATE_PROV, COUNTRY)` | `CUST_ACCOUNT.STATE_PROV`, `CUST_ACCOUNT.COUNTRY` |
| Город | `(CITY, STATE_PROV, COUNTRY)` | `CUST_ACCOUNT.CITY`, `STATE_PROV`, `COUNTRY` |
| Аккаунт (опциональный родительский уровень) | `ACCOUNT_ID` | `CUST_ACCOUNT.ACCOUNT_ID` |
| Получатель (базовый уровень) | `SHIP_TO_ID` | `CUST_ACCOUNT.SHIP_TO_ID` |

Описательные атрибуты получателя: `SHIP_TO_DSC`, `SHIP_TO_DSC_FRENCH`, `SHIP_TO_DSC_DUTCH`.

Дополнительные атрибуты аккаунта из объединённой таблицы: `FIRSTNAME`, `LASTNAME`, `EMAIL`, `PHONE`, `ADDRESS`, `ADDRESS2`, `ZIP_PC`, `FAX`.

Распределение описательных атрибутов по уровням необходимо подтвердить по фактической схеме и данным. Наличие поля в исходной таблице само по себе не доказывает, что оно является атрибутом конкретного уровня.

## 3. Предполагаемая иерархия

`SHIP_TO` — базовый (нижний) уровень. Именно он связывается с фактовой таблицей. Если требуется свёртка от получателя к родительскому аккаунту, `ACCOUNT` включается как необязательный родительский уровень.

Логическое направление от верхнего уровня к базовому:

```text
GEOGRAPHY
└── GEO_ROLLUP
    └── COUNTRY
        └── STATE_PROV
            └── CITY
                └── ACCOUNT (optional)
                    └── SHIP_TO (BASE LEVEL)
                        Key: SHIP_TO_ID
```

**Уточнение направления:** при построении связей инструментом **New Link** связь задаётся от дочернего уровня к родительскому. Поэтому для необязательной связи аккаунта получателя дочерним является `SHIP_TO`, родительским — `ACCOUNT`.

Если фактические данные не подтверждают последовательность `CITY → ACCOUNT → SHIP_TO`, уровень `ACCOUNT` следует исключить из этой иерархии либо пересмотреть модель.

## 4. Ключи и связи между уровнями

| Связь в roll-up | Ключ дочернего уровня | Ключ родительского уровня |
|---|---|---|
| State → Country | `(STATE_PROV, COUNTRY)` | `COUNTRY` |
| City → State | `(CITY, STATE_PROV, COUNTRY)` | `(STATE_PROV, COUNTRY)` |
| Account → City | `ACCOUNT_ID` + подтверждённая географическая привязка | `(CITY, STATE_PROV, COUNTRY)` |
| Ship-To → Account | `SHIP_TO_ID` | `ACCOUNT_ID` |

Города нельзя считать уникальными только по `CITY`: одинаковые названия встречаются в разных штатах и странах. Составной ключ `(CITY, STATE_PROV, COUNTRY)` является предварительным решением и должен быть проверен на реальных данных.

Для каждого перехода необходимо подтвердить функциональную зависимость: один дочерний элемент должен однозначно определять родительский элемент в рамках выбранной иерархии.

## 5. Ragged / Skip-Level hierarchy

Если у части адресов отсутствует `STATE_PROV`, может потребоваться пропуск уровня: `CITY → COUNTRY`.

В Data Modeler для такого перехода предусмотрен инструмент **New Ragged Hierarchy Link**. При экспорте в Oracle OLAP он должен быть представлен как ragged / skip-level hierarchy.

Применять такую связь следует только после проверки, что отсутствие `STATE_PROV` является допустимым свойством данных, а не ошибкой заполнения.

## 6. Связь с фактовой таблицей и кубом

| Параметр | Предварительное значение |
|---|---|
| Fact entity | `GLOBAL.UNITS_FACT` |
| Dimension | `GEOGRAPHY` |
| Присоединяемый уровень | `SHIP_TO` |
| Ключ уровня | `SHIP_TO_ID` |
| Условие соединения | `UNITS_FACT.SHIP_TO_ID = SHIP_TO.SHIP_TO_ID` |
| Role-playing dimension | Не предполагается |

Связь с фактом выполняется на базовом уровне `SHIP_TO`, а не на уровне города, штата или страны. Поля `SHIP_MONTH_ID` и `DELIVERY_MONTH_ID` относятся к отдельному временному измерению и здесь не рассматриваются.

## 7. Проверка перед фиксацией модели

- [ ] `CUST_ACCOUNT` импортирована в Data Modeler; состав колонок сверен с исходным DDL.
- [ ] Проверены уникальность и NULL для ключей всех уровней.
- [ ] Проверены составные ключи `STATE_PROV` и `CITY`.
- [ ] Подтверждена однозначность связей State → Country и City → State.
- [ ] Подтверждена связь `SHIP_TO_ID` → `ACCOUNT_ID`, если уровень Account используется.
- [ ] Проверено соответствие `CUST_ACCOUNT.SHIP_TO_ID` значениям `UNITS_FACT.SHIP_TO_ID`.
- [ ] Базовый уровень `SHIP_TO` подключён к Dimension Shape.
- [ ] Для допустимых пропусков уровней настроены Ragged Hierarchy Links.
- [ ] Определено, будет ли Geography отдельным измерением или частью Customer.
- [ ] Экспорт в Oracle OLAP проверен на ключи, связи и ошибки построения.

## 8. Редакционное примечание

Раздел подготовлен по описанию `CUST_ACCOUNT` в материалах Global11_demo и по предварительному проектному обсуждению уровней географической иерархии. Таблица `CUST_ACCOUNT` описана как CTAS-объект на основе `CUSTOMER_DIM` и `ACCOUNT`; это не подтверждает автоматически все предполагаемые OLAP-уровни и кардинальности.

**До сверки с фактически импортированной схемой GLOBAL в Oracle Data Modeler данный раздел остаётся черновиком.** Он описывает предполагаемый дизайн, а не подтверждённую развёрнутую OLAP-модель.
